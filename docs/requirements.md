# Roslyn Graph - Type extraction requirements

Status: proposed requirements; this document does not assert that the current implementation satisfies them.

Date: 2026-10-15

Implementation and fixture plan: [Phase C - Dependency-complete type graphs](phase-c/phase-c-plan.md). Tracking: [#91 - Method-body dependency extraction oversight](https://github.com/randlee/roslyn-graph/issues/91).

## Scope and terminology

These requirements define static type dependency extraction and recursive graph selection. General cases come first, followed by corner cases, options and verification requirements. **Must** identifies a required capability; **may** identifies a permitted behavior, not an implementation shortcut. Requirement IDs are stable references for implementation, tests and review.

- A **consumed type** is a type required by a declaration, signature, statically bound executable operation or active source-binding context under the selected dependency policy. Merely occurring as text is not consumption. Source binding includes compilation dependencies that need not survive in IL.
- A **root** is an explicitly selected type. Its dependencies include its declarations, members and bodies; selecting a type does not imply a member-level dead-code or runtime-reachability analysis.
- A **registered database** is an explicitly configured, existing graph artifact permitted for dependency resolution. Registration is not permission to download or extract packages.
- A **boundary** is a referenced entity whose outgoing dependencies are unavailable or intentionally not traversed. Its presence is not proof of an empty dependency set.
- **Closure** means a fixed point over the enabled static relationships and available, pinned definitions, or a result explicitly reporting why that fixed point could not be established.

Vocabulary names and configuration spellings remain subject to the Phase C ADRs. The requirements specify observable behavior, not a second competing ontology.

### Completeness and default selection policy

Results must expose separate `selectionComplete` and `dependencyComplete` statuses, with their effective policy and reasons. `selectionComplete` means traversal has reached a fixed point under the configured policy within the registered universe, with no truncation, failed resolution or unknown coverage in admitted definitions. Deliberately unregistered external boundaries do not alone prevent this status. `dependencyComplete` additionally requires the full static baseline and no boundaries, unknown coverage or missing bindings. Neither status certifies build or runtime closure. A partial-policy result can be selection-complete but cannot be dependency-complete.

Framework/BCL types follow the same rules as other libraries: external boundaries by default unless their databases are registered. Registering and admitting a definition increases analysis obligations, not merely available knowledge: metadata-only or otherwise insufficient coverage in an admitted definition blocks `selectionComplete` under the full baseline. There is no monotonic completeness guarantee when registering more databases. The expected selection-complete, dependency-incomplete outcome applies when all admitted definitions have adequate coverage but intentional unregistered external boundaries remain. An explicitly restricted signatures-only policy may be selection-complete using adequate metadata-only databases, but remains dependency-incomplete.

The recommended starting policy keeps framework databases unregistered; selection-complete results still require fully covered admitted component and library definitions. Registering framework databases is an explicit expansion of that analysis obligation.

Attributes are outside the default baseline, so their default exclusion does not itself block either status. Once opted in, missing attribute coverage blocks completeness for that policy. Legitimate no-body declarations do not create coverage gaps; opaque extern/InternalCall implementations and dynamic targets do block `dependencyComplete`. Missing or opaque coverage required by the selected policy also blocks `selectionComplete` in admitted definitions.

New definitions without an explicit follow policy use the full declaration/signature/body baseline; attributes remain off. Explicit restrictive follow lists, including legacy saved lists, are preserved without silently adding new categories and are labeled `partial-policy`. Their excluded categories must be reported. This permits intentional signature-only exploration without confusing it with full static dependency extraction.

## 1. General cases

### Inputs, ownership and identity

| ID | Requirement | Acceptance |
| --- | --- | --- |
| TX-G01 | Extraction must support source-semantic and compiled-assembly inputs with an explicit capability matrix. The existing assembly-backed workflow must gain IL body dependency coverage, not only metadata signatures. | Run the mandatory source and DLL fixtures; publish which facts each mode guarantees. Source-only implementation does not complete Phase C. |
| TX-G02 | Under the full baseline, a selected type must include dependencies from its own declarations and all its applicable members, including non-public members, constructors, accessors and static initialization. Ordinary extraction must not depend on whether a method is called by the sample application. This type-granular over-approximation applies recursively to registered library types: reaching one member of B admits B's other member dependencies, not only that member. | An uncalled private method containing the only use of a fixture type still contributes that dependency, including inside a registered database; unreachable types elsewhere in that database remain absent. |
| TX-G03 | Type identity must distinguish assembly identity, version and applicable artifact identity. Resolution must use compiler/build bindings, not display names or the newest available package. Package version and assembly version must remain distinct. | Same-named types in different assemblies and versions remain distinguishable; a consumer resolves to its bound definition. Ambiguous resolution is diagnosed. |
| TX-G04 | Every dependency must retain its owning declaration, target identity, relationship/reason, extraction mode and source artifact provenance. Type-level dependency edges may project member facts but must preserve an explanation back to those facts. | An exported dependency identifies the originating member and underlying facts, rather than only an unexplained type pair. |

### Executable-body dependencies

| ID | Requirement | Acceptance |
| --- | --- | --- |
| TX-G09 | Body extraction must use semantic bindings for source and resolved IL metadata/signatures for assemblies, not identifier spelling. It must include object and array construction, explicit and inferred locals, and generic instantiations. | `A.Run() => new B().Execute()` selects B although B occurs nowhere in A's declaration or member signatures. Text-only mentions and disconnected decoys are not selected. |
| TX-G10 | Invocation, method-group conversion and field/property/event access must consume the statically bound declaring type, constructed generic arguments and relevant bound signature types. | Calls and accesses whose target types occur only in the body produce dependency facts with their bound identities. |
| TX-G11 | Casts, conversions, type tests and patterns, type tokens (`typeof`/equivalents), `sizeof`, `default`, exception handler/filter types and throw operands must contribute their semantically consumed types. | Each supported category has an isolated target and expected reason; source-erased cases are explicitly distinguished in IL expectations. |
| TX-G12 | Constructor/base initializers, field/property/event initializers and static constructors must participate in extraction. Lambda and local-function bodies must retain lexical ownership and contribute to the containing named type. | Initialization-only and nested-body-only targets are selected with stable owner evidence. |
| TX-G13 | Compiler-bound implicit operations must contribute dependencies, including enumeration, disposal and await patterns. The mandatory baseline must include supported `foreach`, `using`, `await`, `await foreach` and `await using` cases or the corresponding supported-language forms. | Custom pattern members introduce independently asserted dependencies beyond the visible operand type. | TX-G14 | DLL extraction must enumerate applicable MethodDef bodies, including constructors, static constructors, accessors, default interface implementations and generated methods. ### Recursive selection and library databases

| ID | Requirement | Acceptance |
| --- | --- | --- |
| TX-G15 | Recursive type selection must follow enabled declaration, signature and body relationships until a fixed point or an explicit boundary/budget. It must deduplicate work by resolved physical identity without discarding distinct dependency explanations. | A dependency chain, diamond and cycle yield exact expected selected sets and terminate; unrelated types remain absent. |
| TX-G16 | If a referenced library/package has a compatible registered database, selection must resolve the referenced definition and recursively follow its reachable dependencies under the same policy. It must not include every type in that database. | Consumer to package P to registered Q includes reachable P/Q targets, excludes package decoys and records cross-database evidence. |
| TX-G17 | If no compatible registered database exists, retain the external type and assembly/package identity as a boundary. Do not crawl package feeds/caches, acquire packages, extract binaries or recursively collect their internals during graph traversal. | An unregistered package remains a boundary even when its binary exists in a populated cache; intercepted acquisition commands are never invoked. |
| TX-G18 | Database resolution must pin manifests and content hashes and verify artifact presence, integrity, identity, schema compatibility and claimed capabilities before using a registered artifact. Missing, corrupt or hash-mismatched artifacts are not usable definitions. Readable legacy or capability-insufficient artifacts may contribute verified known facts only with explicit incomplete coverage. Registration of a legacy artifact without a manifest must compute a local descriptor and content hash, with coverage marked unknown. Expanding a selection must reuse pins; adopting changed databases requires an explicit refresh. Source databases must not be modified by composition. | Publishing a newer registered artifact does not change pinned expansion; explicit refresh reports changed provenance. Missing/corrupt/mismatched artifacts produce boundaries and diagnostics, never trusted definitions; capability-insufficient stores cannot certify closure. Legacy registration pins bytes without fabricating coverage. |
| TX-G19 | Traversal budgets must apply globally across component and registered-library graphs. Depth counts projected consumed named-type hops: roots are depth zero; member ownership and wrapper plumbing add no hops; crossing a database adds no extra hop. Visit breadth-first with frontiers ordered by stable resolved physical identity. Type limits count admitted physical definitions, including roots; external stubs are counted separately and do not consume that limit. Reject a root set exceeding the type limit rather than silently dropping roots. Every omitted reachable frontier must be reported as truncation. | Depth zero, exact depth/type limits and limits spanning two databases report the expected boundaries and deterministic selected set. Wrapper-rich and cross-database equivalents consume the same depth. Over-budget roots produce an explicit invalid-request error. |

### Diagnostics, schema and explanations

| ID | Requirement | Acceptance |
| --- | --- | --- |
| TX-G20 | Missing/unresolved references and unavailable dependency information must produce structured diagnostics and, by default, allow best-effort extraction to continue with an explicitly incomplete result. TX-O04 defines the explicit strict missing-reference policy. | Missing-reference fixtures retain known facts and diagnostics by default; console quiet mode does not erase persisted diagnostics. Strict behavior is tested under TX-O04. |
| TX-G21 | Results must distinguish policy exclusions, unregistered external boundaries, unresolved/ambiguous bindings, unsupported/opaque body coverage and traversal truncation. Unknown information must not be represented as a definite absence of dependencies. | A mixed fixture preserves each condition through extraction, reduction and export; no aggregate complete status conceals a required unknown region. |
| TX-G22 | Versioned schema/capability metadata must record extractor identity, effective dependency policy, input hashes, extraction mode and body coverage. Independently enumerate candidate executable regions/methods, including source initializer regions, before dependency analysis; record identities, counts and a status for each: analyzed, legitimate no-body, opaque, unsupported, unresolved or failed. An unaccounted candidate makes the result incomplete. Legacy stores lacking coverage evidence must be treated as unknown, not complete. | Candidate enumeration and analysis outcomes reconcile exactly. Intentionally omitting analysis of one method or initializer fails completeness even if all emitted facts look valid; legacy and metadata-only databases cannot certify full static body closure. |
| TX-G23 | Dependency evidence must preserve repeated uses and distinct wrapper paths despite fact deduplication. Source evidence uses stable document identity and spans when available; IL evidence uses module identity, method token and instruction offset when applicable. | Two uses of one target and two generic-argument routes remain separately explainable; machine-specific absolute paths do not define semantic identity. |
| TX-G24 | Identical pinned inputs and effective options must yield stable identities and deterministically ordered semantic output and diagnostics. Effective options affecting extraction must participate in artifact/cache identity. | Repeated runs compare equal after documented nonsemantic normalization; attribute-off artifacts cannot be reused as attribute-complete results. |
| TX-G25 | Build input identity must include target framework, configuration, compiler/SDK, conditional symbols and relevant compilation options. Extract each target-framework/configuration separately unless an explicit union preserves each fact's originating configuration. Inactive conditional regions do not contribute source dependencies. | Multi-target and conditional-compilation fixtures produce distinct pinned inputs and expected graphs; explicit union does not lose fact-level configuration provenance. |
| TX-G26 | Source mode must retain active compiler-binding dependencies even when erased from IL: `nameof`, constant/enum references, optional-argument defaults, conditionally omitted calls and active import/alias/global/static-using directives that the compiler resolves. Type-target directives consume the bound type even when unused; namespace imports retain binding context but never expand namespace types. File/namespace-scoped directives attach to selected types declared within their lexical scope; partial types use the union of applicable directives across all parts. Global/project imports attach to every selected type originating in that compilation. This conservatively retains unused type aliases as compilation-context dependencies. Comments/doc-comment cref are not dependency roots. Directive evidence belongs to file or compilation context, not fabricated method bodies. | Fixtures distinguish source-bound/IL-erased references, inactive `#if`, used/unused aliases, namespace imports, global/static usings, partial declarations across different import scopes and comment-only mentions. An unused global type alias target enters every selected-type closure from that compilation; namespace-only global imports add no type dependency. Conditional calls remain source-binding dependencies even when omitted from emitted IL, with the known erasure reason recorded in the manifest. |
| TX-G27 | ProjectReference targets already present in the input component graph must resolve through their actual pinned build binding; other referenced projects may resolve through registered databases or remain boundaries. Conflicting artifacts with the same assembly identity, including source-mode and IL-mode databases, require an explicit binding/registration mapping; neither mode is preferred arbitrarily. | A project-reference chain resolves pinned component definitions, and competing source/IL artifacts are explicitly mapped or reported ambiguous. |
| TX-G28 | Package-store composition and traversal must stay behind the `rg.py` layer; workbench/viewer clients must not independently open registered stores. Effective registry pins, refresh actions, budgets, strict policy and additional roots must have consistent CLI/wrapper/persisted-configuration semantics wherever exposed. | Contract tests compare effective policies and results across supported entry points; viewer/workbench integration invokes the graph layer rather than bypassing it. |

## 2. Corner cases

These requirements extend the general cases; they are not substitutes for their happy-path coverage.

| ID | Requirement | Acceptance |
| --- | --- | --- |
| TX-C01 | Recursive wrappers must preserve array rank, pointer chains, constructed generic definitions, argument ordinals and repeated routes to the same target. | Nested generic/array/pointer fixtures include every named constituent; repeated generic arguments retain distinct routes. |
| TX-C02 | Type parameters must retain declaration owner and ordinal and must not become fabricated external concrete types. Method and enclosing-type generic parameters must remain distinct. | Nested generic types/methods with reused parameter names resolve correctly and traverse their declared constraints. |
| TX-C03 | Overloads, generic arity, conversions differing by return type, nested generic ownership and relevant ref/out/in/ref-readonly distinctions must not silently merge distinct declarations or signatures. | The identity fixture produces distinct identities where the language/metadata distinguishes declarations; legacy ambiguity is reported rather than repaired by guessing. |
| TX-C04 | Function-pointer signatures must preserve managed/unmanaged conventions and ref-bearing parameter/return shapes, recursively including nested callables and wrappers. | Callable fixtures verify exact constituent types, order and signature identity, not just a display string. |
| TX-C05 | Bound extension methods, user-defined conversions/operators, explicit/implicit interface implementations, overrides and static interface members must retain the actual statically bound relationship. | Fixtures distinguish bound owners and decoys; no test assumes enumeration of every possible runtime dispatch target. |
| TX-C06 | Partial declarations, generated source, top-level statements, async/iterator lowering, closures and local functions must have documented stable ownership. Generated dependencies present in the extraction input must not disappear solely because they lack a user-written method declaration. | Fixture facts identify the original/generated artifact and owner; source/IL ownership differences are documented and independently checked. |
| TX-C07 | A legitimate no-body declaration must be distinguished from unavailable, unsupported or opaque body information. Abstract/interface declarations need not have bodies; default interface bodies do. Extern/native implementations remain opaque. | Metadata-only/ref-only inputs, default interface methods and extern fixtures have distinct coverage outcomes. |
| TX-C08 | Source and IL capability differences must be explicit: optimization and compilation can remove source references or introduce generated implementation dependencies. IL closure must not be presented as source-rebuild closure. | Debug/Release fixtures have reviewed mode-specific expected results; unexplained differences fail the gate. |
| TX-C09 | Cross-database resolution must account explicitly for type forwarding, retargeting, target framework and reference-versus-runtime assembly mappings where available. Ambiguous or incompatible matches must not be selected arbitrarily. | Versioned package fixtures resolve an explicit compatible mapping or report a boundary/diagnostic; matching names alone do not pass. |
| TX-C10 | Cross-database cycles, shared definitions and conflicting identities must terminate and preserve provenance without collapsing distinct versions. | Controlled graph/assembly fixtures verify visited identity, deterministic closure and global limits without requiring invalid circular project references. |
| TX-C11 | Invalid/unresolved symbols, malformed inputs and partial extraction failures must be surfaced at the affected scope and aggregated into result status. No failure may be silently converted to an empty complete graph. | Isolated failure fixtures produce explicit failure/incomplete outcomes; a malformed input may fail when meaningful extraction cannot continue. |
| TX-C12 | C# and Visual Basic support must have an explicit feature matrix, including non-equivalent language constructs. Unsupported constructs outside the mandatory baseline require specific diagnostics. | Both language projects exercise supported general body cases; silently skipping a required language case fails completion. |
| TX-C13 | By-reference parameters/returns and ref-like types must preserve their type identity and dependency constituents. The schema ADR must define handling of required and optional custom modifiers, including modifier-type dependencies and their effect on signature identity; modifiers must not be silently stripped when doing so changes binding or meaning. | Fixtures cover byref locals/parameters, ref and ref-readonly returns, ref-like types and required/optional custom modifiers. Assert target traversal and signature distinctions according to the documented policy; unsupported modifier semantics remain explicit limitations. |
| TX-C14 | Dynamic operations and VB late-bound sites must record operation-level opaque runtime targets while retaining every statically known receiver, argument and result dependency. Their presence must never be interpreted as automatic discovery of runtime targets, in either extraction mode. | C# dynamic and VB Option Strict Off fixtures preserve known facts and explicit opaque coverage; inability to infer runtime targets remains visible without making dynamic inference a required capability. |
| TX-C15 | Nullable value types, tuple/ValueTuple constituents, anonymous types and stackalloc must expose their actual constituent dependencies and stable ownership according to source/IL capabilities. Nullable reference annotations must not create fabricated concrete types. | Dedicated fixtures test each shape, repeated tuple targets and mode-specific generated types; target and provenance assertions accompany wrapper checks. |
| TX-C16 | Embedded interop/NoPIA type-equivalence resolution is unsupported in Phase C and must produce an explicit limitation rather than silently treating copied metadata as an authoritative equivalent definition. | An interop fixture reports the unsupported equivalence and cannot certify dependency completeness for that region. |

## 3. Optional categories and explicit policy controls

An optional category is enabled only through an explicit recorded policy. It must not weaken requirements for enabled categories or silently disable the default body/signature baseline. Explicit restricted policies are permitted as defined above and must remain labeled partial-policy.

| ID | Requirement | Acceptance |
| --- | --- | --- |
| TX-O01 | Attribute extraction and attribute-origin dependency traversal must be disabled by default. Provide an explicit positive opt-in, proposed as `--include-attributes`, across CLI, Python wrapper, persisted configuration and reduction. Reading compiler-semantic attributes/metadata for binding, ownership or identity is allowed when disabled, but must not emit attribute-origin dependencies. Signature custom modifiers follow TX-C13 independently of attribute collection. | Default extraction and reduction exclude attribute-only dependencies; explicit opt-in includes them. Ordinary references remain included. Async/iterator ownership, readonly/ref-like/init/nullability and pseudo-custom metadata fixtures retain their semantics with attributes off without leaking attribute-class dependencies. |
| TX-O02 | Attribute opt-in must cover supported assembly/module/type/member/return/parameter/type-parameter sites, attribute classes and typed constructor/named arguments, including type tokens, enum values and typed arrays. | Each site and argument kind has provenance and typed targets; formatted argument text alone does not satisfy extraction. |
| TX-O03 | Attribute policy migration must respect explicit prior selections, reject contradictory flags and include the effective setting in artifact identity. An attribute-free database cannot satisfy an opt-in request without regeneration or an explicit capability diagnostic. | Test deprecated explicit exclusion, include/exclude conflict, saved-definition migration, cache separation and insufficient database coverage. |
| TX-O04 | Strict missing-reference failure must be an explicit opt-in. It triggers on unresolved/ambiguous bindings, missing explicitly pinned inputs, corrupt artifacts and hash mismatches. Default behavior remains report-and-continue where meaningful extraction is possible. | Exercise each trigger and non-trigger with both default continue/report and explicit strict settings, on applicable source-semantic and IL inputs. | TX-O05 | Exhaustive external-package acquisition/traversal is a future option, not a Phase C deliverable or implicit fallback. Merely referencing or registering a package must not enable exhaustive collection. | No Phase C default or registered-database operation acquires dependencies or imports unreachable package types. Any future option requires a separate design and tests. |
| TX-O06 | Additional roots supplied for known reflection/plugin/native integration dependencies must be recorded as explicit user knowledge, not claimed as automatically discovered static facts. Automatic runtime discovery is outside Phase C. | Any explicitly supplied roots remain distinguishable in provenance; limitation fixtures do not falsely report runtime completeness. |

## 5. Boundaries and non-goals

Static type closure is necessary for many extraction workflows but is not a guarantee that selected code can be rebuilt or executed. Source files can contain unselected declarations; builds also require project settings, generated sources, packages, resources and assembly boundaries. Execution can depend on reflection, runtime dispatch, dynamic loading, native libraries, configuration and assets that static type relationships cannot fully determine.

Phase C does not require a full call graph, whole-program virtual dispatch analysis, arbitrary source reconstruction, deployment packaging, or exhaustive external crawling. These limitations must remain visible in documentation and result explanations rather than being hidden behind a generic `complete` label. Completeness claims must always state the selected static policy, extraction capabilities, pinned database universe and any remaining boundaries.
