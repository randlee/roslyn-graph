# Roslyn Graph - Static migration inventory requirements

Status: proposed requirements; this document does not assert that the current implementation satisfies them.

Date: 2026-10-15

Implementation and fixture plan: [Phase C - Static type inventory for code migration](phase-c/phase-c-plan.md). Tracking: [#91 - Method-body dependency extraction oversight](https://github.com/randlee/roslyn-graph/issues/91).

## Scope and terminology

These requirements define a thorough, categorized static inventory of analyzed libraries for deciding what code moves from A to B. Include every type/member in selected root libraries and follow type relationships into other already-analyzed libraries. Transitive selection must be iterative and cycle-safe, not implemented through recursive dependency calls. General cases come first, followed by corner cases, options and verification requirements. **Must** identifies a required capability; **may** identifies a permitted behavior. IDs remain stable; retired interoperability scope is explicitly marked rather than presented as unfinished work.

- A **consumed type** is a type required by a declaration, signature, statically bound executable operation or active source-binding context under the selected dependency policy. Merely occurring as text is not consumption. Source binding includes compilation dependencies that need not survive in IL.
- A **root** is an explicitly selected type, or any type in a library explicitly selected for full inventory. Its dependencies include its declarations, members and bodies; selecting a type does not imply a member-level dead-code or runtime-reachability analysis.
- A **registered database** is an explicitly configured, existing graph artifact permitted for dependency resolution. Registration is not permission to download or extract packages.
- A **boundary** is a referenced entity whose outgoing dependencies are unavailable or intentionally not traversed. Its presence is not proof of an empty dependency set.
- **Closure** means a fixed point over the enabled static relationships and available, pinned definitions, or a result explicitly reporting why that fixed point could not be established.

Vocabulary names and configuration spellings are implementation decisions. Record consequential choices with the code changes; no separate ADR is required for every increment. These requirements specify observable behavior, not a second competing ontology.

### Completeness and default selection policy

Results must expose separate `selectionComplete` and `dependencyComplete` statuses, with their effective policy and reasons. `selectionComplete` means traversal has reached a fixed point under the configured policy within the registered universe, with no truncation, failed resolution or unknown coverage in admitted definitions. Deliberately unregistered external boundaries do not alone prevent this status. `dependencyComplete` additionally requires the full static baseline and no boundaries, unknown coverage or missing bindings. Neither status certifies build or runtime closure. A partial-policy result can be selection-complete but cannot be dependency-complete.

Framework/BCL types follow the same rules as other libraries: external boundaries by default unless their databases are registered. Registering and admitting a definition increases analysis obligations, not merely available knowledge: metadata-only or otherwise insufficient coverage in an admitted definition blocks `selectionComplete` under the full baseline. There is no monotonic completeness guarantee when registering more databases. The expected selection-complete, dependency-incomplete outcome applies when all admitted definitions have adequate coverage but intentional unregistered external boundaries remain. An explicitly restricted signatures-only policy may be selection-complete using adequate metadata-only databases, but remains dependency-incomplete.

The recommended starting policy keeps framework databases unregistered; selection-complete results still require fully covered admitted component and library definitions. Registering framework databases is an explicit expansion of that analysis obligation.

Attributes are outside the default baseline, so their default exclusion does not itself block either status. Once opted in, missing attribute coverage blocks completeness for that policy. Legitimate no-body declarations do not create coverage gaps. Runtime-resolved targets and native implementations are outside static inventory scope: retain their declarations and statically known references, but do not infer their runtime behavior or require a runtime-target diagnostics subsystem. Missing required managed-body analysis does block completeness in admitted definitions. Both statuses describe only the declared static inventory scope.

New definitions without an explicit follow policy use the full declaration/signature/body baseline; attributes remain off. Explicit restrictive follow lists, including legacy saved lists, are preserved without silently adding new categories and are labeled `partial-policy`. Their excluded categories must be reported. This permits intentional signature-only exploration without confusing it with full static dependency extraction.

No depth or type-count limit applies by default, for either full inventory or graph selection. Positive limits are optional explicit arguments and may be recorded in saved definitions. Preserve the existing `max_depth = 0` meaning of unlimited depth; remove the implicit 1,500-type default. Cycle detection, iterative expansion and batched queries must provide complete results without relying on an arbitrary cap.

## 5. Boundaries and non-goals

The deliverable is a thorough categorized inventory for deciding what to move from A to B, including dependencies in already-analyzed libraries. It is not executable reconstruction. Source files and runtime deployments may require more than the inventoried static relationships.

Phase C does not require runtime inference, COM/NoPIA or specialized interoperability handling, a full call graph, arbitrary source reconstruction, deployment packaging or exhaustive external crawling. Do not turn excluded areas into mandatory diagnostics or fixture projects. Completeness claims state the static policy, extraction capabilities, pinned analyzed-library universe and any missing required analysis or explicitly requested limits.
