## Finding 0: current stores have no project provenance triples

`dt:definedInAssembly / rg:builtFromProject` (5adfb5c) exists only in v3 artifacts. Every artifact in the store
is v2, so the store has none of these triples. The locator therefore derives the project from the manifests:

1. the type's named graph (`GRAPH ?g`) is a component's `graphIri`;
2. the component's `manifestPath` (solution `components`, or view `overlayComponents`) gives `origin.repository`,
   `origin.commit`, `dirtyHash`, `build.project` and `build.solution`;
3. a v2 `build.project` is relative to the profile root, not the repository: `CalibrationXCore/.../X.csproj` with
   repository `F:\_r2609\p3-cli\CalibrationXCore`. The project is `repository.parent / project` when that file
   exists, else `repository / project`. A v3 path is repository-relative.

The provenance triples remain a cross-check for v3 artifacts.

## Experiment 1: Compile items

`compile_items.py --manifest <view manifest> --output compile-items.json --jobs 4`

| Measure | Result |
|---|---|
| Projects | 59 of 59 evaluated; no failures; all SDK-style; no `.vbproj` in this solution |
| Time | 25.3 s summed over projects, 0.52 s for the slowest; 6.8 s wall time with 4 jobs |
| Compile items | 4807 `.cs` files |
| Linked files outside the project directory | 1: `Microsoft.NET.Test.Sdk.Program.cs` from the NuGet cache, added to `Radiant.P3Cli.Tests` by a target. It declares `AutoGeneratedProgram` |
| Under `obj/` | 0 |
| Projects with no Compile items | 2: `Radiant.Camera.SVK61` and `Radiant.RPC.Annotations` |

Three things are needed for the evaluation to match the build. Without the first two it silently gives different
preprocessor symbols:

1. **Solution context.** P3 projects import `$(SolutionDir)Common.targets`, which pulls in `CommonTargets/TT3X.targets`
   and the platform files that set `TRUETEST3X`, `RADIANT_DATA_NUGET`, `NUGET_PACKAGE_INCLUDE`, `TT19_OR_GREATER`
   and more. A project evaluated alone has no `SolutionDir`, skips the whole chain, and gets only `DEBUG;TRACE`.
   The evaluation passes `SolutionDir`, `SolutionPath`, `SolutionName`, `SolutionFileName` and `SolutionExt` for the
   manifest's `build.solution`, as a solution build does. With them, 56 of 59 projects get the TT3 symbols. The
   other 3 are `Radiant.P3Cli.Tests`, which does not import the chain, and the two Radiant overlay projects, which
   are built from their own solutions.
2. **Implicit symbols.** `NET`, `NET10_0`, `NET10_0_OR_GREATER`, `NETCOREAPP` and the other framework symbols are
   added by the SDK target `AddImplicitDefineConstants`, not at evaluation. `-t:AddImplicitDefineConstants` with
   `-getProperty:DefineConstants` returns the complete list. Running the target also returns Compile items added by
   targets (the test SDK's `Program.cs` above).
3. **Build properties.** `Configuration`, `TargetFramework` and `Platform` from the manifest.

Known limit: a constant that a project appends inside some other target, which runs later, would still be missing.
None of the 337 P3 `.props`, `.targets` and `.csproj` files sets `DefineConstants` inside a `<Target>`, and the audit below accounts
for every not-found type. The Roslyn command below takes the symbols as input, so it does not fix this
limit either.

## Experiment 2: declaration scan accuracy

`scan_accuracy.py --store ... --manifest ... --compile-items compile-items.json --graph-nt measurement-database.nt`
scans every Compile item with the prototype lexer (`csharp_scan.py`) and its preprocessor evaluator. It then
matches every component type of the store (`dt:fullName`) to the declarations in its own project.

Statuses: `found` (declared in a Compile item), `compiler-generated` (a name segment starts with `<`; matched to
the files of the enclosing named type), `compiler-generated-unowned` (`<Module>`, `<PrivateImplementationDetails>`
and other types with no named owner), `not-found`, `nuget`.

| Scope | Types | found | compiler-generated | unowned | not-found | nuget | partial (several files) |
|---|---|---|---|---|---|---|---|
| All component types | 12,595 | 6,412 | 4,051 | 356 | 576 | 1,200 | 711 |
| `measurement-database` graph | 929 | 685 | 202 | 0 | 3 | 39 | 55 |
| Random 300 source types (seed 20261013) | 300 | 160 | 112 | 13 | 15 | 0 | 12 |

Scan time: 12.9 s for 4806 files.

**Every not-found was examined** (`not_found_audit.py`). Of 803 not-found and unowned rows, 801 have no
declaration of that name in any Compile item of the repository. They were produced by a source generator, a weaver
or the compiler:

| Producer | Rows |
|---|---|
| Enum generator: `*Extensions`, `*JsonConverter` | 309 |
| Compiler: `<Module>`, `<PrivateImplementationDetails>`, `<>z__ReadOnlyArray<T>` | 254 |
| Radiant data generator: `*Struct`, `*ResultStruct`, `*PropertyStruct` | 132 |
| `Editable*Properties` generator | 44 |
| `GeneratedRadiantDataRegistration`, `SchemaManifest`, `StructManifest` | 28 |
| `*CInterop`, `CInteropEnumsPython` | 18 |
| Fody: `*_ProcessedByFody` | 4 |
| Other generator output (`SuppressGeneratedEnumContractAttribute`, `Equals.Helpers`, `ImageStatsHeader` and similar) | 12 |

The remaining 2 are not scanner misses either. `AutoGeneratedProgram` is declared in the Compile item outside the
repository, and `<>z__ReadOnlySingleElementList<T>.Enumerator` is compiler-generated and matched by name only.
The 3 not-found types in the graph are generator output (`EditableSaveToMeasurementDatabaseProperty`,
`AnalysisImageTypeEnumExtensions`, `AnalysisImageTypeEnumJsonConverter`).

So, with the right preprocessor symbols, **the lexer missed nothing**. Getting there took three corrections, and
each one is a design input:

| Run | found | Cause of the misses |
|---|---|---|
| Both branches of every `#if` scanned | 6,406 | braces inside `#if`/`#else` in method bodies unbalanced the scope stack (6 types in `CameraExtensions.cs` named wrongly) |
| `#if` evaluated with evaluation-time `DefineConstants` | 6,358 | no implicit `NET*` symbols: `#if NET10_0_OR_GREATER` blocks dropped |
| ... plus `-t:AddImplicitDefineConstants` | 6,401 | no `SolutionDir`: TT3 symbols missing (`#if TRUETEST3X`, `#if RADIANT_DATA_NUGET` blocks dropped) |
| ... plus solution context | **6,412** | none |

**Decision: B2 uses Roslyn instead of the lexer.** The lexer works, but each language rule (preprocessor
expressions, nested generics, VB) is one more thing to get right by hand. Roslyn already has these rules. The
extractor gains a command that takes the files, language version and preprocessor symbols from the MSBuild step,
parses with `CSharpParseOptions`/`VisualBasicParseOptions` (no MSBuild, no references), and returns each declared
named type with file and line. Names are formatted with the extractor's own `TypeNameFormat`, so they match
`dt:fullName` by construction. roslyn-diff (sister repository) parses the same way, but it derives symbols only from
target framework names. That misses every TT3 constant, so its approach is used rather than its code.

## Experiment 4: scope adherence

### Tool level (done, no model needed)

`probe_backend.mjs` constructs openwiki's agent backend (`OpenWikiLocalShellBackend`) exactly as the planner and
page workers do, on a clone with the generated scope, and calls every file tool:

| Check (10-type and 200-type file-level scopes) | Result |
|---|---|
| `read` of every scope file | allowed |
| `read` of about 200 sampled files outside the scope | all denied (203/203, 204/204) |
| `ls` walk from the root | surfaces exactly the scope files (10, 170) |
| `grep` from the root | matches only scope files |
| `glob **/*` from the root | refused ("Unbounded root globbing is disabled") |
| shell `execute` | refused: only `pwd` and `git rev-parse HEAD` are allowed |
| write outside `openwiki/` | denied; write inside `openwiki/` allowed |

The agent has no way to read outside a file-level scope. This settles open decision 2 for enforcement. How well the
model keeps its prose to the brief is still to be measured (below).

**OpenWiki defect found.** With a search directory, `glob` returns paths relative to that directory
(`/Lib/Layers/X.cs`). The ignore filter then tests those relative paths against root-anchored rules, so with a
deny-all chain every directory-scoped `glob` returns nothing, even for scope files. `glob` from `/` with a
directory-prefixed pattern (`Radiant.Simulation.Image/**/*.cs`) works and returns exactly the 10 scope files. This
is not a leak, but it hides scope files from one discovery tool. Workaround in the design: the brief lists every
file path and tells the agent to use `ls`, `grep` or root-anchored `glob` patterns. It is worth reporting upstream.

### Model level (blocked here; run on Radiant.Data)

The model-level run was done on a smaller target with the `openai-chatgpt` provider:
[openwiki-run-radiant-data-2026-10-13.md](openwiki-run-radiant-data-2026-10-13.md). The P3 runs below remain

`run_openwiki.py` runs `openwiki code --init -p` on a fresh clone at the manifest commit, with:
- `fs_trace.mjs`, which logs every path the process opens under the repository;
- `usage_proxy.py`, a pass-through proxy set as `ANTHROPIC_BASE_URL` that logs tokens and tool calls per API call.

It reports reads outside the scope, tool counts, tokens, time, pages, and how many briefed types the wiki mentions.

`401 invalid x-api-key`, and the shell's `ANTHROPIC_API_KEY` also returns 401 directly against
`api.anthropic.com/v1/models`. No other provider key is configured.

OpenWiki needs a branch: a detached `HEAD` fails with "Unable to resolve repository HEAD for fingerprinting". The
harness checks out a local branch at the commit.

## Changes to the design

Applied to [README.md](README.md) and [implementation-plan.md](implementation-plan.md) in this layer:

1. Project resolution uses the component manifests (finding 0). Provenance triples only cross-check.
2. The MSBuild step evaluates with solution context and `-t:AddImplicitDefineConstants`, and also returns
   `DefineConstants` and `LangVersion`.
3. Declarations come from a Roslyn `declarations` command in the extractor, not a Python lexer.
4. `locationStatus` gains `compiler-generated` (owner's files), and `not-found` becomes `generated` (declared in no
   Compile item). Generated types open nothing instead of their whole project directory, because 801 of 803 are
   generator or compiler output and opening their projects would expose everything.
5. The brief tells the agent how to discover files despite the `glob` defect.
